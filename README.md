# CAN serializer

Firmware for the CAN serializer board (STM32G473CC, three MCP2562FD transceivers).
The board is a 3-channel CAN FD to USB adapter that speaks the **gs_usb** protocol used by
candleLight adapters. On Linux it shows up as `can0`, `can1` and `can2` with the in-kernel
`gs_usb` driver. Nothing needs to be installed on the host.

## Features

- 3 independent CAN FD channels (ISO), each up to 1 Mbit/s nominal and 8 Mbit/s data.
- Bitrates, FD mode, listen-only, loopback and one-shot are set per channel from the host.
- Hardware timestamps (1 µs) on every received frame and TX echo.
- Bus state reporting (warning / passive / bus-off) as SocketCAN error frames. Bus-off
  recovers automatically.
- Identify: `ethtool -p canX` blinks that channel's LEDs.
- Works with [tuican](https://github.com/Bridiro/tuican) (`--interface gs_usb`) and other
  libusb-based gs_usb tools. Windows binds WinUSB automatically (Microsoft OS descriptors).

## Build and flash

Requires [PlatformIO](https://platformio.org/) and `STM32_Programmer_CLI` (STM32CubeProgrammer)
with an ST-LINK on SWD.

```sh
pio run                  # build (env: release)
pio run -t upload        # flash over SWD
pio run -e debug         # debug build
pio check                # clang-tidy on Core/*/serializer
```

## Using it on Linux

```sh
# CAN FD: 500 kbit/s arbitration, 5 Mbit/s data
sudo ip link set can0 up type can bitrate 500000 dbitrate 5000000 fd on

# Classic CAN only
sudo ip link set can1 up type can bitrate 1000000

candump -t a can0
cansend can0 123##1DEADBEEF   # FD frame with bit rate switch
cansend can1 123#DEADBEEF
```

Optional per-channel modes: `listen-only on`, `loopback on`, `one-shot on`.
Use `sample-point` / `dsample-point` to adjust the timing the kernel picks (for example
`dsample-point 0.75`).

The FDCAN kernel clock is 80 MHz, so every standard rate divides exactly:

| Phase | Exact rates |
| --- | --- |
| Arbitration | 125k, 250k, 500k, 1M |
| Data (FD) | 1M, 2M, 4M, 5M, 8M |

Rates that don't divide 80 MHz evenly (for example 3 Mbit/s) cannot be hit exactly.
Transmitter delay compensation is enabled automatically above 2.5 Mbit/s.

## LEDs

Each channel has an RX and a TX LED.

| Pattern | Meaning |
| --- | --- |
| Short flash | A frame was received / transmitted |
| Both solid | Channel is bus-off (recovering) |
| Both blinking together | Identify requested by the host |
| Sweep at power-up | LED self-test |

## Code map

Application code lives in `Core/Src/serializer/` and `Core/Inc/serializer/`. Everything
else under `Core/` and `Drivers/` is generated by STM32CubeMX from `CAN-serializer-sw.ioc`.

| File | Role |
| --- | --- |
| `serializer.c` | Entry points called from `main.c` (`serializer_init`, `serializer_loop`). |
| `usb-device.c` | Minimal USB device on HAL PCD: descriptors, EP0 requests, WinUSB descriptors. |
| `gs-usb.c` | gs_usb protocol: vendor requests, bulk IN/OUT pipes, channel start/stop requests. |
| `can-bridge.c` | Runs the FDCANs: configuration, RX, TX with echoes, error states, bus-off recovery. |
| `frame-queue.h` | Lock-free single-producer / single-consumer frame queue. |
| `gs-usb-protocol.h` | gs_usb wire structs and constants (match the Linux driver). |
| `timestamp.c` | 32-bit µs counter on TIM2. |
| `leds.c` | Activity / fault / identify LEDs. |

### Data flow and execution contexts

```text
CAN bus -> FDCAN RX FIFO -> FDCAN IRQ (prio 1) -> IN queue (256 frames) -> USB IRQ (prio 2) -> bulk IN
host    -> bulk OUT -> USB IRQ -> channel TX queue (16) -> FDCAN IRQ -> TX FIFO -> CAN bus
                                                         TX event -> echo -> IN queue
main loop: applies start/stop requests (FDCAN re-init) and drives the LEDs
```

- All CAN and USB work happens in interrupts. The main loop only reinitialises an FDCAN when
  the host starts or stops a channel, because `HAL_FDCAN_Init()` polls with timeouts.
- The three FDCAN interrupts share one priority, so together they are the single producer of
  the IN queue.
- Bulk OUT is only re-armed while every channel TX queue has room. A busy bus slows the host
  down (USB NAK) instead of dropping frames.
- If the host stops reading, received frames are dropped and the next delivered frame carries
  the gs_usb overflow flag (`candump` shows it as an RX overflow error).

### Limits

USB full speed tops out around 1 MB/s. Three buses saturated at 5 Mbit/s with 64-byte frames
produce more than that, so very heavy simultaneous traffic on all channels will overflow.
Typical vehicle loads are well below this.

## Regenerating with STM32CubeMX

The project is generated with the **Makefile** toolchain; PlatformIO builds the same sources.
After regenerating:

- Application hooks are inside `USER CODE` blocks (`main.c`, `stm32g4xx_it.c`) and survive.
- The FDCAN1/2/3 IT0 and USB_LP interrupts are enabled in the `.ioc`. Keep FDCAN at
  priority 1 and USB at priority 2.
- **TIM2** is used directly by `timestamp.c`. Don't enable it in CubeMX.
- **CRS** (HSI48 trimming from USB SOF) is enabled in `usb-device.c`, not in the `.ioc`.
- SPI1, I2C1, USART1 and USART2 are initialised but not used yet (reserved for sensor
  debugging).

## Git Hooks
> [!Warning]
> Make sure to add all the needed directories in TARGET_DIRS

The pre-commit hook formats staged files in `Core/Src/serializer` and `Core/Inc/serializer`
with clang-format. Generated CubeMX code is left alone.

To setup git hooks in your local repository you will have to execute the following commands:

```sh
chmod +x hooks/pre-commit
```

```sh
git config core.hooksPath hooks/
```
